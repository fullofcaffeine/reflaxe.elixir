## Executive Verdict

Reflaxe.Elixir is credible for **controlled production pilots inside its documented, pinned paths**.
It is not yet ready for a general `1.0` stability claim.

The review found no known P0 issue. It did find P1 release blockers in four different categories:

1. compiler semantics;
2. build and generated-file lifecycle correctness;
3. product/support contract and licensing;
4. evidence from testing one release candidate in independent real-world projects.

This is not a verdict that the compiler architecture or recent Reflaxe convention work was wasted.
The source/package split, target-owned `_std` layout, deterministic package checks, AST ownership, and
framework integration are useful foundations. The remaining work is what turns strong repository
evidence into a stable consumer promise.

## Review Method

The review combined:

- a repository audit of compiler tests, Mix integration, generated-output ownership, release policy,
  support matrices, security controls, licensing, examples, and the Beads dependency graph;
- an independent GPT 5.6 Pro adversarial pass asked to find reasons *not* to call the project 1.0;
- primary-source checks of Haxe and Gleam claims used in public positioning;
- executable evidence already present in CI, package parity, runtime examples, and browser sentinels.

The independent model was a second reviewer, not an authority. Findings were retained only when they
mapped to repository evidence or a clearly missing decision. Passing tests remain stronger evidence
than prose, and external adopter behavior remains stronger evidence than either model opinion.

The review did **not** include qualified legal advice, a third-party security audit, a large independent
production deployment, or controlled performance testing across representative hardware. Those gaps
are stated rather than inferred away.

## What Is Already Strong

### Target-Native Product Model

The compiler emits `.ex` source into the normal Mix pipeline. Generated and hand-written modules can
coexist through ordinary module/function contracts, and typed externs describe the Haxe side of an
existing Elixir boundary. Haxe is absent from the deployed node.

This supports a valuable adoption ladder: one typed domain function, one bounded Phoenix feature, a
shared browser/server domain, or a larger Haxe-first surface. Teams are not required to replace an
entire application to evaluate the compiler.

### Compiler And Runtime Evidence

The repository has broad snapshot categories, negative fixtures, function-result invariants,
Haxe-authored ExUnit runtime tests, selected upstream `unitstd`, strict generated-Elixir compilation,
examples, source/package parity, and Phoenix browser sentinels. That is materially stronger than a
transpiler validated only by golden text.

### Release Engineering

Current releases are tied to the fully gated commit, built reproducibly, checksummed, attested, and
tested as installed packages. The Reflaxe source `_std` versus packaged `.cross.hx` layout is documented
and tested instead of being left as contributor folklore.

### Phoenix And LiveView Integration

Phoenix/LiveView is the strongest framework area. The project has typed assigns and extern surfaces,
HXX/HEEx authoring, generated router and LiveView shapes, Mix tests, examples, dogfood upgrades, and
real-browser smoke. That makes Phoenix-native gradual adoption the most defensible initial market.

## P1 Findings At The Baseline

### 1. Known Executable Semantic Defects

**Closed after the baseline review.** Reducer control flow (`3qh.23`), nested dynamic comprehensions
(`3qh.24`), and nested reducer lexical state (`3qh.25`) are fixed at compiler AST boundaries. The
Haxe-authored `test/runtime/loop_control_accumulators` and
`test/runtime/nested_dynamic_comprehensions` suites preserve source-level regression fidelity rather
than bypassing the compiler with target injection.

### 2. Incremental Mix Builds Did Not Track Every Effective Input

**Closed after the baseline review (`0yn.1`).** Mix now stores a deterministic content fingerprint of
recursive HXML, direct classpaths, resources, resolved libraries and package descriptors, toolchain
identity/standard library, relevant environment, explicitly declared macro inputs, and
output-affecting configuration. Tests cover rebuild and no-op behavior, same-timestamp edits,
timestamp-only touches, removed roots, and the todo app's `src_shared` graph. Arbitrary macro reads
outside that graph must be declared with `:extra_inputs`.

### 3. In-Place Generated Output Needs One Fail-Closed Owner

**Closed after the baseline review (`0yn.2`).** Compiler output is now staged and formatted before a
transaction publishes it. `_GeneratedFiles.json` records every owned path and content hash; unowned
collisions and modified owned files fail before live output changes; stale removal and Mix clean use
the same record; and an interrupted transaction is recovered before the next build. Tests cover first
generation, unchanged and owned updates, namespace moves, stale deletion, collisions, clean,
interruption, legacy-manifest upgrade, source rollback, and source/package parity. Isolated output
remains a supported deployment choice, but in-place generation no longer relies on source markers or
directory scans for ownership.

### 4. The Stable Surface Is Documented But Not Enumerable

The repository contains feature, stdlib, support, versioning, and API documents, but no single checked
inventory connects every stable language form, annotation, extern, flag, Mix task, generated
module/function name and call shape, framework API, and version bound to executable evidence. Without
that inventory, “1.0 compatibility” cannot be reviewed or changed coherently.

Frameworks, toolchains, language combinations, and internal surfaces can still use a bounded stable
set. The Haxe standard-library portion is stricter after the product decision above: every applicable
public runtime API must be implemented and tested rather than placed outside the major-1 contract.

### 5. Broad OTP Wording Exceeds Current Failure Evidence

**Closed after the baseline review (`0yn.3`).** The
[OTP Support Contract](../04-api-reference/OTP_SUPPORT_CONTRACT.md) now names the runtime-proven local
Process, Task, and Agent operations and the narrower application/child-spec boot evidence. A focused
Haxe-authored runtime lane compiles generated Elixir with warnings as errors and runs on the minimum
and primary toolchains. Custom GenServer callbacks, broad supervisor failure/restart behavior,
Registry, mailbox/monitor behavior, distributed OTP, and hot upgrades are explicitly outside the 1.0
promise. Compiling an API-shaped module is no longer presented as lifecycle proof.

### 6. Licensing Is A Product Decision

The repository is GPL-3.0, including compiler, Mix integration, externs, and support code unless stated
otherwise. Generated applications may ship modules derived from repository runtime/stdlib sources.
The existing [Licensing & Distribution](../06-guides/LICENSING_AND_DISTRIBUTION.md) guide correctly
avoids legal conclusions, but broad commercial positioning needs a qualified decision about output and
runtime distribution. Possible outcomes include keeping GPL-3.0 with clear guidance, an output/runtime
exception, separately licensed runtime pieces, or dual licensing; engineering review cannot choose the
lawful answer by itself.

### 7. External Release-Candidate Testing And Final Approval Are Missing

Project-local CI does not prove the complete consumer lifecycle. A candidate must be installed into a
clean external workspace, adopted gradually in an existing Phoenix tree, upgraded from the previous
release, checked for stale-file/collision behavior, run on minimum and primary toolchains, and rolled
back by immutable tag. The major-1 manifest must remain fail-closed until a durable review accepts that
evidence.

### 8. Complete Haxe Stdlib Support Is Now A Product Requirement

The baseline review treated a classified stdlib subset as enough for a bounded 1.0. That is no longer
the intended product promise. The current matrix still documents fail-fast or partial behavior for
identity maps, linked-list sorting, serialization/templates, caller-buffer IO, parts of SSL and
lifecycle handling, and `sys.db.*`. The module-level gap report also measures local target files, not
API behavior.

`haxe.elixir.codex-0yn.10` now owns an API-level inventory and the implementation/conformance work.
Official Haxe fallback remains a valid implementation when it is tested; complete support does not
mean copying every upstream file. Runtime-relevant entries may not remain unsupported, partial,
unknown, or untested. Compile-time and other-target-only declarations need narrow source-backed
classification and the appropriate compile-time evidence. See
[Standard Libraries And Packages](stdlib-and-package-ecosystem.md).

## P2 Findings And Residual Risk

- The effective Elixir AST pipeline is large and contains repair/replay families. Phase invariants,
  scoped ownership, and byte-parity checks reduce risk, but tasks such as
  `haxe.elixir.codex-3qh.22` should keep moving repairs toward their earliest semantic owner.
- The Haxe-authored stdlib runtime suite must become warning-clean so new warnings cannot hide in
  existing noise (`haxe.elixir.codex-0yn.7`). This is now part of the P1 complete-stdlib gate rather
  than residual polish.
- CI security coverage is useful but partial. Gitleaks downloads now require the exact SHA-256 stored
  in the repository, changed bytes fail a guard test, and every external Action must use a full commit
  SHA. `@fullofcaffeine` owns monthly and pre-release dependency review (`0yn.6`). CodeQL still does
  not analyze Haxe or Elixir, advisory databases can lag, and the upstream build and hosting systems
  remain trusted dependencies.
- The repository has benchmark infrastructure but not a stable compile-time SLO. The 1.0 candidate
  needs a regression comparison, not a universal hardware promise.
- The maintainer and adopter base is small. No test suite can substitute for independent production
  time, incident handling, and ecosystem feedback.

## Product Positioning

### The Defensible Thesis

Reflaxe.Elixir is a typed authoring layer for selected Elixir application surfaces:

1. It emits reviewable Elixir source that stays in Mix, Phoenix, and normal BEAM operations.
2. It can be adopted one module or feature at a time and removed along the same boundary.
3. Haxe offers ADTs, pattern matching, structural records, higher-order functions, conditional
   compilation, and typed macros; an Elixir-flavored Haxe style maps more directly than a heavily
   imperative or object-oriented style.
4. A deliberately portable domain layer can also target JavaScript, enabling selected browser/server
   sharing without pretending Phoenix or DOM code is portable.
5. The complete applicable Haxe standard library keeps Haxe behavior, with visible helpers when exact
   behavior cannot be represented as a direct Elixir call.

### Comparison With Gleam

The project should not market itself as universally “better than Gleam.” Gleam is already a stable,
purpose-built functional language with first-class Erlang and JavaScript targets. Its smaller immutable
language and mature dedicated ecosystem are advantages.

Reflaxe.Elixir can be the better fit when a team specifically values:

- generated Elixir source inside an existing Mix/Phoenix tree;
- direct Phoenix/Ecto macro and DSL shaping;
- module-by-module adoption and rollback;
- Haxe expression/build macros and a broader language model;
- existing Haxe code or selected sharing with Haxe's wider target ecosystem.

Gleam is the better fit when enforced immutability, language simplicity, mature 1.x stability, and one
cohesive Erlang/JavaScript language contract matter more than generated Elixir or Phoenix macro access.
These distinctions follow the projects' own documentation: Haxe's
[language features](https://haxe.org/documentation/introduction/language-features.html),
[targets](https://haxe.org/documentation/introduction/compiler-targets.html), and
[macros](https://haxe.org/manual/macro.html); and Gleam's
[FAQ](https://gleam.run/frequently-asked-questions/) and
[externals guide](https://gleam.run/documentation/externals/).

## Definition Of A Defensible 1.0

`1.0.0` should mean all of the following, and no more:

- the enumerated stable subset has no known P0/P1 semantic defect;
- every public Haxe standard-library API applicable to generated Elixir programs is supported, with
  no runtime-relevant entry marked unsupported, partial, unknown, or untested;
- source and installed package behavior agree for representative stable paths;
- every effective build input invalidates output deterministically;
- generated-file writes, stale deletion, clean, upgrade, and rollback are ownership-safe;
- Phoenix, Ecto, OTP, stdlib, toolchain, and operating-system bounds are explicit;
- generated output is warning-clean and reviewable, with required helpers explained;
- licensing/distribution policy is deliberate and visible before installation;
- one unchanged release candidate has passed a defined test period in clean external projects;
- the major-1 approval record names the exact evidence and residual risks.

It does not mean every combination of Haxe constructs, framework version, operating system, target,
third-party BEAM library, or possible output optimization is supported. It does mean the applicable
public Haxe standard library is complete.

depends on the final complete-stdlib review and still has to incorporate the human licensing decision.
External testing depends on that support list and a clean, immutable release candidate. Final
approval depends on the external test results. The current machine-readable sequence is
`bd graph haxe.elixir.codex-0yn`.

## Review Again When Evidence Changes

Repeat an adversarial readiness review after the support-list and ownership tasks close, before the
release candidate is selected, and after external testing. The useful question is not “does the
README sound production ready?” It is “which exact promise still lacks executable or independently
observed evidence?”
