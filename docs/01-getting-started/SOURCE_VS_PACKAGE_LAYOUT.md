# Source Checkout vs Release Package Layout

Reflaxe.Elixir has one compiler implementation and one set of target stdlib sources. The repository
and the installed release arrange those same files differently because Haxelib packages expose only
one classpath.

This is packaging, not a development backend versus a production backend.

## The short version

| Mode | Intended use | How Haxe sees target std overrides |
| --- | --- | --- |
| Source checkout | Compiler development, repo tests, unreleased integration testing | Explicit `src`, `std`, and `std/elixir/_std` classpaths |
| Built package | Normal application development and releases | One package `src` classpath containing Reflaxe-generated `.cross.hx` files |

Both modes compile the same authored Haxe implementation through the same Reflaxe.Elixir compiler,
AST pipeline, semantic passes, and printer.

## A concrete example

The repository authors the Elixir implementation of `haxe.Exception` here:

```text
std/elixir/_std/haxe/Exception.hx
```

Repo-local HXML makes `std/elixir/_std` visible before Haxe starts typing. Haxe therefore selects that
file instead of the upstream extern declaration.

When creating a release, Reflaxe reads `haxelib.json`'s `reflaxe.stdPaths`, merges those paths into the
package classpath, and copies files from a path ending in `_std` with the target suffix:

```text
src/haxe/Exception.cross.hx
```

The function bodies are copied unchanged. The `.cross.hx` suffix tells Haxe that the file is the
implementation for Reflaxe's Haxe 4 `cross` target. It does not select another Elixir compiler or
another exception implementation.

This is the layout generated by Reflaxe's own `new` template and implemented by its `build` command.
The same source/package split is documented by `reflaxe.rust` and by the `reflaxe.ocaml` package in
the hxhx repository. Those compilers also keep authored overrides in a target `_std` tree, put the
source roots on development HXML classpaths, and reserve flattened `.cross.hx` files for packages.

## Why Haxelib needs a built layout

A Reflaxe compiler naturally has multiple source roots:

- compiler code under `src`;
- target APIs under `std`;
- replacements for upstream Haxe modules under a target `_std` root.

Reflaxe's documentation notes that Haxelib libraries are allowed one source path. `reflaxe build`
solves that distribution constraint by producing a package with one merged classpath. Normal users
can then write only:

```hxml
-lib reflaxe.elixir
```

Consumer install commands use `www.github.com` for the release asset URL. Lix 15.12.x intercepts
bare `github.com` HTTPS URLs as repository dependencies, but the release download path is a built
Haxelib archive rather than source. The `www` host follows GitHub's normal release redirect through
Lix's generic HTTPS archive resolver.

Raw `haxelib dev` or `lix dev` points at the unbuilt source layout. By itself, that exposes `src` but
not `_std` early enough to replace every upstream module. External source-checkout testing must run:

```bash
REFLAXE_ELIXIR_CHECKOUT=/absolute/path/to/reflaxe.elixir
npx lix dev reflaxe.elixir "$REFLAXE_ELIXIR_CHECKOUT"
"$REFLAXE_ELIXIR_CHECKOUT/scripts/dev/configure-source-checkout-hxml.sh" . "$REFLAXE_ELIXIR_CHECKOUT"
npx lix download
```

The helper renders the same scoped HXML used by this repository. It does not build or modify compiler
sources.

## Why local tests do not build first

Building a package before every test would be slower and would make it easier to test stale copied
files. It would also make source positions point at package artifacts instead of the files being
edited.

The normal development loop therefore compiles current source directly. That is also how Reflaxe's
own test command is structured: it supplies the compiler classpath and configured std paths to Haxe.

Package behavior is a separate required validation lane. It catches different failures:

- a missing or incorrectly ordered `stdPath`;
- an override that was not converted to `.cross.hx`;
- package metadata that still describes the multi-root source tree;
- a consumer build that works only because the repository's scoped HXML is present.

## How we prove both modes agree

`npm run test:haxelib-package` is the boundary test. It:

1. Compiles a fixture from the explicitly wired source checkout.
2. Runs Reflaxe's package build and installs the resulting zip in isolation.
3. Compiles the same fixture using only the installed `-lib reflaxe.elixir`.
4. Compares the generated Elixir file set and contents, excluding only volatile manifests and source
   path metadata.
5. Verifies the package contains generated `.cross.hx` overrides and no raw `_std` source tree.

The broader snapshot, strict Elixir, runtime, PhoenixHx, and dogfood suites continue to validate the
compiler itself. The package parity check validates that distribution did not change what it emits.
