# Router DSL (`@:routes` / `@:route`)

## Summary

Reflaxe.Elixir supports two router authoring styles:

1. `@:routes` on a `@:router` module (recommended)
2. `@:route` on individual static functions (legacy/manual)

Use `@:routes` for new code. It is clearer, easier to validate, and works best with typed controller/action references.

## Recommended: `@:routes` on `@:router`

```haxe
import reflaxe.elixir.macros.HttpMethod;

@:native("MyAppWeb.Router")
@:router
@:build(reflaxe.elixir.macros.RouterBuildMacro.generateRoutes())
@:routes([
  {
    name: "home",
    method: HttpMethod.GET,
    path: "/",
    controller: controllers.PageController,
    action: controllers.PageController.home
  },
  {
    name: "dashboard",
    method: HttpMethod.LIVE,
    path: "/dashboard",
    controller: live.DashboardLive,
    action: live.DashboardLive.index
  }
])
class MyAppRouter {}
```

Compiles to:

```elixir
defmodule MyAppWeb.Router do
  use Phoenix.Router

  scope "/", MyAppWeb do
    pipe_through :browser
    get "/", PageController, :home
    live "/dashboard", DashboardLive, :index
  end
end
```

### Why this is preferred

- Typed controller/action refs are checked by the Haxe compiler and macro validation.
- Route definitions stay in one declarative list.
- Optional helper functions can be generated by `RouterBuildMacro.generateRoutes()`.

## Route object fields

- `name` (required): route helper function name.
- `method` (required): `HttpMethod.*` (preferred) or legacy string.
- `path` (required): route path string.
- `controller` (required except `LIVE_DASHBOARD`/`MAILBOX`): controller/live module.
- `action` (required except `LIVE_DASHBOARD`/`MAILBOX`): action function.
- `pipeline` (optional): `"browser"` or `"api"` override.

## Supported methods

Prefer `reflaxe.elixir.macros.HttpMethod`:

- `GET`
- `POST`
- `PUT`
- `PATCH`
- `DELETE`
- `LIVE`
- `LIVE_DASHBOARD`
- `MAILBOX`

String methods are still accepted for compatibility, but enum values are safer and easier to refactor.

## Typed refs vs string refs

Use typed refs by default:

```haxe
{ controller: controllers.UserController, action: controllers.UserController.index }
```

String refs are still supported for interop/migration only:

```haxe
{ controller: "Elixir.ExternalWeb.UserController", action: "index" }
```

Choose strings only when the target is intentionally outside the typed Haxe surface (for example, external Elixir modules you do not model in Haxe).

Note: use fully-qualified type paths in `controller`/`action` references (for example
`controllers.UserController`), not imported short names, so macro-time controller/action validation can resolve them reliably.

## Legacy/manual style: `@:route`

Manual `@:route` is still supported, but it is a legacy/manual path:

```haxe
@:native("MyAppWeb.Router")
@:router
class MyAppRouter {
  @:route({method: "GET", path: "/", controller: "controllers.PageController", action: "home"})
  public static function home(): String {
    return "/";
  }
}
```

Compiles to:

```elixir
defmodule MyAppWeb.Router do
  use Phoenix.Router

  get "/", PageController, :home
end
```

This style is useful for incremental migration or handwritten router glue. For new code, prefer `@:routes` with typed controller/action references.

## Generation model

- Router emission is driven by `@:routes` metadata on `@:router` modules.
- `RouterBuildMacro.generateRoutes()` is a helper that can generate route helper functions and perform extra validation.
- The compiler lowers router metadata to Phoenix router macros (`get`, `post`, `live`, `scope`, `pipe_through`) in generated Elixir.

## Practical guidance

- Use `@:native("MyAppWeb.Router")` for Phoenix naming conventions.
- Keep routes in `@:routes` for readability and code review clarity.
- Use enum methods and typed refs unless you intentionally target external Elixir modules.
- Keep `@:route` only when needed for legacy/manual patterns.
