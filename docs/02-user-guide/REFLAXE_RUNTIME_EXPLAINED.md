# The `reflaxe_runtime` Define (Compiler Development Only)

`reflaxe_runtime` is a Haxe compilation define used when the Reflaxe compiler's own
source code must be typed as ordinary Haxe code instead of running only in macro mode.
It is not an Elixir runtime mode, deployment profile, or application dependency.

## Application Builds Do Not Need It

Normal Reflaxe.Elixir applications should use `-lib reflaxe.elixir`. The library
configuration supplies the `elixir` target marker and initializes the compiler:

```hxml
-lib reflaxe.elixir
-cp src_haxe
-D elixir_output=lib
Main
```

Do not add `-D reflaxe_runtime` to new application HXML files. Existing projects may
leave it temporarily while upgrading because the define remains compatible, but it is
redundant and can be removed.

This follows the convention generated by `reflaxe new`:

- consumer/test HXML files load the target library and its initialization macro;
- `DevEnv.hxml` defines `reflaxe_runtime` so editors and direct compiler-development
  checks can see implementation guarded by `#if (macro || reflaxe_runtime)`.

Reflaxe.Rust and Reflaxe.OCaml also keep the define out of normal consumer HXML files.

## When It Is Needed

Use `-D reflaxe_runtime` only when developing the compiler and deliberately typing its
implementation outside macro mode, for example:

```hxml
# DevEnv.hxml inside a Reflaxe compiler repository
-D reflaxe_runtime
-lib reflaxe
-cp src
reflaxe.elixir
```

Repository snapshot fixtures that bypass `-lib reflaxe.elixir` and type compiler source
directly may also use it. Direct target fixtures should prefer `-D elixir` when they only
need to select Elixir APIs.

## It Does Not Control Emitted Runtime Helpers

The define does not opt an application into a large compatibility runtime. Small modules
such as `Reflaxe.Elixir.HaxeThrow` and `Reflaxe.Elixir.HaxeFloat` are emitted only when
the compiler needs them to preserve Haxe semantics. Their inclusion is controlled by the
compiler and normal dead-code elimination, not by the application's use of
`reflaxe_runtime`.

Reflaxe.Elixir still prefers compile-time lowering and target-native APIs:

- hashing APIs map to BEAM primitives such as `:crypto.hash/2`;
- maps and iterators lower to ordinary Elixir operations when semantics permit;
- dynamic access stays at typed JSON, params, or `DynamicAccess` boundaries.

## Source and Package Parity

The repo-local `haxe_libraries/reflaxe.elixir.hxml` and the packaged
`extraParams.hxml` both supply the same `elixir` target marker. CI compiles a
representative project through both layouts and compares generated output, so removing
the application define does not create different development and release semantics.
